# Farert DB の設計・実装手順

DB は Windows(MFC)・iOS・Android・CLI・WASM(PWA) が共有する。**正本は Google スプレッドシート**で、
`db/` の生成物(`jrdbNewest.txt` / `jrdbNewest.db`)はそこから作る。仕様書は
`specs/Core/database.md`(生成フロー)と `specs/Core/database-schema.md`(全テーブル・ビット定義)。
`specs/` は farert リポジトリでは未追跡なので、更新してもコミットされない点に注意。

## 生成フロー(2026-10 に実測で確認)

```
スプレッドシート(SPREADSHEET の SpredsSheetsId / シートごとの gid)
  → down_spr_as_text.sh: 各シートを TSV で *.tmp に保存(*.tmp は .gitignore)
  → mktext: linesNewest clinfarNewest rule69 rule70_new rule86 fare2 brt の順に連結して jrdbNewest.txt(追跡対象・直接編集禁止)
  → scripts/jr_db_reg.py jrdbNewest.txt <年> → jrdbNewest.db
  → scripts/node_list.py jrdbNewest.db > scripts/node_list.txt(t_node 再生成)
  → Makefile が配布: app/Farert.ios/Farert/jrdbnewest.db, app/win_mfc/.../res/jrdbnewest.db,
    app/Farert.android/.../assets/routeDB/jrdb.dat(zip の jrdbNewest.db エントリだけ更新)
  → WASM: ../farert-wasm で scripts/copy-sources.sh → npm run build:wasm → ../farert-pwa で pnpm copy:wasm
```

- `make update` = `clean`(*.tmp *.db 削除)+ ダウンロード + 生成 + 配布。スプレッドシートを変えたらこれ。
- `make`(clean なし)は lines 系 *.tmp があるとダウンロードをスキップする。さらに **jrdbNewest.txt にはレシピがない**ので、
  *.tmp を手で変えても txt は作り直されない。その場合は下記「ローカル検証」の連結コマンドで txt を作ってから
  `rm jrdbNewest.db && make`。
- macOS は大文字小文字を区別しないので、Makefile の `cp jrdbNewest.db .../jrdbNewest.db` は既存の `jrdbnewest.db` を上書きする(名前はそのまま)。

## 作業前のベースライン確認(必須)

手元の *.tmp がスプレッドシートの最新と一致している保証はない。生成し直すと関係ない差分が混ざるので、
変更前に scratch で再生成してコミット済み DB と比べる。

```bash
D=<scratchpad>/dbwork; mkdir -p $D; cp -R db/scripts db/EULA.txt db/*.tmp $D/; cd $D
{ echo "# DO NOT EDIT THIS FILE DIRECTLY. このファイルを直接編集しないでください"; cat EULA.txt
  for f in linesNewest clinfarNewest rule69 rule70_new rule86 fare2 brt; do cat $f.tmp; echo ""; done; } > jrdbNewest.txt
diff -q jrdbNewest.txt <repo>/db/jrdbNewest.txt            # 同一なら tmp は最新
python3 scripts/jr_db_reg.py jrdbNewest.txt 2026 > reg.log && python3 scripts/node_list.py jrdbNewest.db > /dev/null
diff <(sqlite3 <repo>/db/jrdbNewest.db .dump) <(sqlite3 jrdbNewest.db .dump)   # 期待: t_dbsystem の日時だけ
```

差分が日時以外にも出るなら、先に `make update` で最新化する(またはユーザーに確認する)。

## テーブルを追加する手順

1. **仕様を先に書く**: `specs/Core/database-schema.md` にテーブル定義と元データの場所を追記する。
2. **jr_db_reg.py**:
   - `create table` を他テーブルと同じ場所(`t_toica_range` の後など)に追加。参照列は `not null references ...` にしておくと、
     駅名・路線名の誤記が `NOT NULL constraint failed` で生成時に検出できる。
   - `dispatch` 辞書に `'t_xxx': self.reg_t_xxx` を追加し、`reg_t_xxx(self, label, linitems, lin)` を書く。
   - 駅名は `same_staion("金山(中)")` で `(name, samename)` に分けて `t_station where name=? and samename=?` で引く。
3. **データ(スプレッドシート)**: 既存シートにセクションを足すのが簡単(例: rule69 シートに `*t_rule160_6`)。
   - 書式: 先頭列が `*t_xxx` の行でセクション開始(ラベルは `\w+` で切り出し)、`#` 行はコメント、
     空行は無視、`//end` か次の `*` 行で終了。列はタブ区切り。
   - Claude はスプレッドシートを編集できない。貼り付け用 TSV を用意してユーザーに追加してもらう。
4. **ローカル検証**: ユーザーの反映を待たずに検証するときは、`db/rule69.tmp` 等にセクションを追記し、
   上の連結コマンドで `db/jrdbNewest.txt` を作り直して `rm db/jrdbNewest.db && (cd db && make)`。
   スプレッドシート側に同じ内容が入れば、後の `make update` でも同じ DB になる。
5. **DB の差分確認**: `git show HEAD:db/jrdbNewest.db` と `.dump` 比較し、追加テーブル以外に差がないこと。
6. **エンジン側**(C++ `app/alps/alpdb.cpp` と Java `app/Farert.android/.../org/sutezo/alps/*.java` を 1対1 で):
   - **旧 DB にはテーブルがない**(iOS/MFC/Android は jrdb2014〜2017 等も同梱)。
     C++ の `DBS::compileSql()` は prepare 失敗で無効な `DBO` を返すだけ(ASSERT なし)なので `isvalid()` で抜ける。
     Java の `RouteDB.db().rawQuery()` は例外を投げるので `RuntimeException` を捕捉して非該当にする。
   - `alpdb.h` を変えたら CLI は `make clean && make`(Makefile がヘッダ依存を追わない。farert-cli スキル参照)。
7. **回帰**: `farert -exec` の前後 diff(farert-route-engine-debug スキル)と `./test/run_java_regression.sh`。
   `-exec` に新データを使う代表経路を `test/unix/common/test_exec.cpp` に足す(Java 回帰も同じ経路を回る)。
8. **配布**: Makefile が iOS/MFC/Android を更新。WASM/PWA は上記フローで再ビルド・コピー
   (`grep -c '/Users/' static/farert.js` が 0 であること)。

## 落とし穴

- **t_jctspcl に規則の案内用データを入れない**。lines シートの `branch` 行(先頭列 `x`→type=1, `6`→type=6)は
  `t_lines` の lflg(bit31 / 下位8bit=id)にも反映され、`Route::add()` の分岐特例変換や
  160条の4 の分割入力判定(`JCTSP == RetrieveJunctionSpecific(...)`)に効く。案内だけのデータは別テーブルにする
  (例: `t_rule160_6`)。
- `jrdbNewest.txt` を直接編集しない(次の `make update` で消える)。直すのはスプレッドシート。
- `t_lines.lflg` のビットは `database-schema.md` の表が正。新しいビットを立てる前に未使用か確認する。
- DB を変えたら iOS / MFC / Android(jrdb.dat)/ WASM の4系統すべてに反映されたかを確認する。
  iOS・MFC は `cmp db/jrdbNewest.db <copy>` で同一性を見られる。

## 実例: t_rule160_6(2026-10)

旅客営業規則第160条の6(折返し直通列車の区間外乗車)の区間データ。列は `id / station_id_c / station_id_d / line_id1 / line_id2`。
rule69 シートの `*t_rule160_6` セクション(`# id / 左方の駅c / 右方の駅d / 路線1 / 路線2`)から生成し、DB に入っている。
**エンジン(C++/Java)は現在このテーブルを使っていない**(案内文の実装は一度入れたが取り消した)。
使うときは上記手順 6〜8(旧 DB への配慮、C++/Java 1対1、-exec と Java 回帰)に従う。
